## 使用方式

每条需求有稳定编号，便于在讨论和实现说明中引用。直接编辑表格的“需求决策”和“实现说明”两列；需要展开时，在对应分类下添加按编号命名的说明。新增需求使用新的编号，不因删除或调整顺序而重排已有编号。

- 需求决策可填写：（保留）旧行为、（采用）新行为、调整后保留、暂缓、不迁移。初始统一为“待定”，不表示已经批准实现。
- 实现说明可填写：负责模块、数据结构、方法、配置作用域、生效时机、异常行为和验收条件。初始“—”表示尚未填写。
- 接口覆盖是设计评估，不是实现完成状态。审查接口的方法体留空；部分可运行原型存在于同目录其他文件中，见 [原型说明](prototype.md)。
- `metadata` 或通用回调只是承接位置；缺少字段语义、业务操作和状态规则时，仍标为部分覆盖。
- 本文是需求设计清单，不是实施 issue；后续拆分实施任务时遵循仓库 `.scratch/` 与 triage 约定。

| --- | --- |
| 已覆盖 | 公开数据结构、操作和职责已明确考虑到需求；不代表已经实现或通过验收。 |

> 上下文压缩的设计：
>
> 总体压缩方法（提示词，要求内容）等内容参考 Python 版本，作如下改进：
>
> - 上下文压缩摘要将成为真的 Message 信息： Message 增加一种“abstract" 消息，在渲染 ContextMessage 时，如果找到这类消息，那么只渲染该消息并忽略前方除了 system prompt 外的所有对话历史。在计算占用量等情况下，同样不渲染前方消息。这应当能通过接口设计简单的实现，因为占用量计算是根据 ContextMessage 而不是原始 Message 来的。
> - 如果修改 abstract 类型消息的前文，可以考虑提示是否要修改（真的吗？不提示也行），如果修改则删除该消息，在下次触发压缩（不管是 token 上限还是手动压缩）时重新获得 abstract 信息。下次触发压缩不必保证其压缩范围和之前被删除的摘要一致：按照对话进展的范围自然压缩即可。
> - ContextMessage 格式化时，必须携带 reasoning 记录和历史工具调用记录：因此，必须保证 Message 存储的 tool call 消息和模型的返回是大致一致，格式化后，是可以被下轮对话接受的。
>   这不仅是为了上下文压缩的设计，也是为了普通对话中模型能看到曾经工具调用的历史和结果。
>
> 请在对话中与我讨论这样的设计如何。

滚动摘要的覆盖范围由其在有序历史中的插入位置表达，不重复持久化覆盖终点或依赖定位表。精确重放供应商原始报文与保留工具结果语义仍是不同需求；同响应分组和工具调用 ID 需要由消息结构保留。

> 更多的双形态定义：
>
> 双形态角色是指拥有多套 live2d 模型，多种提示词，多种语音模型、多种参考音频的角色，其几乎所有配置都是两套。
>
> 这有什么意义呢？在原著动漫里，祥子确实有黑祥（mujica 时期被生活毒打了…然后对其他人脾气不好）和白祥（Crychic 时期，对其他人非常客气和主动，简直是白月光）的形态。
>
> 睦在 mujica 中包含一般睦，morits 两个形态，剧中定义是不同人格，有不同的对话习惯、口癖和语气风格，基本共享记忆，也可以视为双形态角色。
>
> 总之，双形态角色可以代表角色的不同典型表现阶段，或者多重人格角色的多个人格。
>
>
>
> 技术上：双形态角色可以通过特殊标识位 isDoubleForm 标识，并通过 defaultForm 存储默认访问哪套数据。
>
> 其可多存储内容包含所有配置，即 live2d 模型、角色名称、角色描述、语音模型、参考音频（路径、语言与文本）、主题色、图标。
>
> 可以为 Character 设计大量通用 getter，例如 getDefaultLive2dModel，接收额外的形态枚举参数，单形态角色忽略该参数（是否传入皆可）并默认返回 live2d 模型，多形态角色在传入时返回对应形态内容，不传入时使用 defaultForm 对应形态的一套配置。



> 额外问题：live2d 默认模型设计
>
> 曾经的 live2d 默认模型和其他模型存储在不同文件夹下，因此很难切换默认模型。在 JS 版本中，我希望默认模型只是一个标签，和其他所有模型平级存储在文件夹下，Character 根据默认标签返回默认模型，并允许修改默认模型。
>
> 在迁移时，可以将 Python 版本的 extra model 和 live2d model 平级存放，并将 live2d model 指定为初始的默认模型。

LIVE-06 已决定按对话、按形态保存；Python 的 `ChatMeta.character_forms` 与 `live2d_form_models` 可作为迁移依据。[Electron 原型说明](prototype.md) 中的全角色共享换装属于待收敛行为。原文引用的 ADR-0052 当前工作区不存在，不再把失效链接作为决策依据。

## 已确认的设计选择

确认日期：2026-10-07。以下记录多轮讨论中已经明确接受的决定；正式签名和文件结构已于 2026-10-08 写入接口，业务方法体仍为空。尚未同意的方案只放在下一节，不用“已确认”替代后续讨论。

### 设置归属、options 与执行输入

关联：CHAT-03、RUN-03、AGENT-01 至 AGENT-04、SET-01 至 SET-06。

- Chat、Turn 和 Message 是持久化数据；Conversation 是指定 Chat 的运行时修改所有者，不公开可任意改写的快照。
- 删除粒度不明的 setDefaults。按业务分组提供 setScenario、setTools、setWorldbookInfo、setCharacterSelection、setGenerationOptions 等操作，不为每个标量增加方法。每个操作只接受自己的配置，但同时负责必要的保存、资源和能力更新。
- 参数对象命名为 options。Conversation 在开始执行时按全局配置、Chat 配置、本次 options 的顺序解析，之后只向各模块投影所需材料；不让同一个大对象沿调用链逐级覆盖不明来源的同名默认值。
- 模型和连接必须在请求前确定，凭据由后端连接配置解析；角色资源由 CharacterCatalog 解析。不需要让每个业务调用重复传入密钥、地址和文件路径，也不能为缺失的必需材料猜默认值。凭据不进入 Chat 或归档。
- 小剧场情境、说话风格和互动设定属于 Chat.meta，使用类型明确的结构并按角色 ID 关联，拼入 User Prompt，与 Python 对齐。执行时固定采用的材料不改变配置归属。
- Agent 负责提示、总执行预算和工具循环；LLM 适配负责供应商请求参数。Schema 校验结构，业务校验身份、语言、情绪和本轮演出目录。使用 AI SDK 和 Models.dev 的已验证接入方向，能力来源、覆盖和未知状态需保留。

### 历史修改与最后一轮重生成

关联：CHAT-04 至 CHAT-07、AGENT-05、WORLD-03。

- 原地编辑只开放手动发送的用户内容、角色台词及翻译；不编辑 reasoning 和工具记录。工具结果采用 UserMessage 容器不意味着它成为可人工编辑的用户文本。编辑保留后续历史，不自动请求 LLM。发声材料改变时旧音频失效。
- 删除以 Turn 为单位，包含选中 Turn 和后面的全部内容；不再开放删除一句话。分支和回溯也保持 Turn 粒度。
- 原地编辑、删除或回溯历史一经受理，使该 Chat 旧组全部未消费 async 结果失效，包括已排队和尚未返回的请求；已入历史的结果不因此删除。单纯重合成语音、修改背景等不改变对话语义的操作不触发此失效。校验失败不改变结果资格。
- 重新生成只对最后一个 Turn 开放；受理时必须核对目标仍是最后一轮。保留原输入、附件或内部事件输入，以及 Chat 的参与角色、模式和固定用户人格。
- 重生成创建新的 Turn 和 UUID，替换旧 Turn；保留输入内容不要求保留旧 TurnId。TurnId 在同一次生成及其 Agent Loop 内稳定，终止或完成后不重新进入 running。由此不再为重生成另设一个内部轮次执行编号；正式接口声明已同步，并返回新 TurnId，尚未实现。
- 重新解析当前连接、模型、采样、语言、翻译、提示词、小剧场设定、角色形态和能力、工具、世界书及新回复的语音配置，形成新的执行快照。不隐式复用上次只在 createTurn(options) 中传入的临时覆盖。
- 新执行替代旧回复、reasoning 和工具过程记录；已经创建的提醒、导出文件等副作用不自动撤销。重新生成可以产生新的提醒；同一次工具调用的通信重试仍须去重。
- 该重生成语义在 Electron 设计中更新 ADR-0033 的旧配置复用约定，见 [ADR-0049](../../docs/adr/0049-regenerate-last-electron-turn-with-current-settings.md)；不改变 Python 当前实现。
- 编辑并重发只允许最后一轮，沿用人工可编辑输入的范围；移除旧末轮，按编辑后的输入及当前配置创建新 TurnId／新组，旧组保持失效。Conversation 应先校验新输入和末轮身份，再统一受理替换，不让调用方执行两个独立的删除／创建请求；校验或受理保存失败不丢失旧轮，共用附件不能提前回收。早期原地编辑仍保留后文，不触发生成。

### Message 容器与只读投影

关联：CHAT-01、CHAT-02、CHAT-04、RUN-02、RUN-07、AGENT-10、TTS-02。

- Message 包含 UserMessage、AssistantMessage、ToolResultMessage 和 AbstractMessage。AssistantMessage 的有序 parts 可以包含 ReasoningPart、ToolCallPart 和 DialoguePart；DialoguePart 保存有序 CharacterLine。一次 assistant 响应的分组不拆开，Turn 可包含多次响应及其工具结果。
- UserMessage 通过 source 区分真正的手动用户输入、async 交互结果及提醒等内部输入，不另增 EventMessage。来源由后端受理入口确定；不能依据消息容器名或模型协议的 user role 判断是不是手动发送。现有 Turn.trigger 与新来源字段须统一语义，不能分别维护互相矛盾的来源。
- ToolCallPart 保存模型提出的调用，包括调用 ID、工具名和参数；ToolResultMessage 保存对应结果或错误，使用同一调用 ID 关联，不在调用项内重复持久化结果。没有结果与成功返回空值不能混淆。
- 嵌套存档是权威来源。展示、LLM 请求、摘要及语音／演出按各自用途读取它，投影不成为可独立修改的第二份历史。供应商所需的同响应分组和调用关联不能被展示投影抹掉。
- 提供按原顺序提取台词、reasoning、工具调用及查询工具结果的只读 helper；可以接受 Turn 或 AssistantMessage，声明见 message-projections.js，返回只读有序条目。语音材料仍由 Conversation 准备，Speech 不读取完整 Turn。
- 投影条目由记录中的稳定身份派生，不能每次投影生成新 ID 或以数组下标作为身份。内容编辑仍定位权威记录，经 Conversation 的受限操作完成。
- 允许消费端接收完整的扁平投影，不要求调用者自行管理局部显示更新；这不规定每次都重新复制全部历史、跨进程传输整份存档或重建全部投影项。React 的具体性能策略留待实现及测量，不增加后端业务状态。

### 摘要位置与上下文占用

关联：AGENT-07、AGENT-08。

- 保留原始存档，只从模型上下文排除已压缩历史。abstract 是正式的累计摘要记录，放在最后一个被压缩 Turn 的消息末尾、近期保留历史之前。
- 摘要覆盖其位置之前的全部历史；只投影最后一份有效摘要和它之后的原始消息。不重复持久化覆盖终点、父摘要 ID 或定位表。system、当前小剧场设定等本次配置材料仍按正常请求规则构造。
- 压缩仅处理已结束的完整 Turn，至少保留最后一个 Turn 不压缩。编辑前文时移除后方摘要；之后按当时进展重新压缩，不要求复现旧压缩范围。分支、截断自然按位置携带或移除摘要。
- 摘要失败保留旧有效状态，不破坏原文；按预算策略降级，仍无法容纳必需输入时明确失败。手动压缩不制造角色回复。
- 上下文检查复用实际请求准备逻辑，涵盖角色、人格、历史、当前输入、工具、输出约束和附件；区分估算值、未知值、模型上限来源和实际 usage。查询不隐式执行摘要、上传或工具。
- 二次复核已确认手动压缩互斥生成和历史修改、允许历史回放；自动压缩属于当前生成内部阶段，不增加持久化定位字段。

### 工具执行与协议记录

关联：CHAT-02、AGENT-05、AGENT-10、RUN-06、TOOL-01 至 TOOL-06。

| 执行模式 | 当前工具等待什么 | 最终结果去向 |
| --- | --- | --- |
| async | 前端／宿主交互请求被可靠登记和受理 | 结果仍有效且受理后新建内部 Turn，不消费草稿 |
| block-async | 前端／宿主交互完成、取消或失败 | 当前 Agent Loop |
| sync | 后端工具完成、取消或失败 | 当前 Agent Loop；本地执行仍可返回 Promise |

- async 返回 accepted 及请求身份，表示受理，不冒充实际完成；同一个结果不能既继续原工具又新建回复。交互结果按请求及来源执行关联，避免重复回流。
- async 完成结果先入队，等当前 Turn 的生成、语音和演出全部完成且允许受理后合并已就绪结果，通过一条 UserMessage 创建新 Turn；不在原 Turn 中注入，不等待同轮其他工具返回，也不要求问题全部答完。
- async 结果有效性按下述轮次组管理。组内任一 Turn 被终止或新的手动消息被受理后，该组全部未消费结果失效，包括尚未返回的请求；自动 Turn 正常开始或结束不会使本组其他结果过期。
- 每个 Chat 可以持有独立 Agent；每次执行固定工具集合。工具依赖由后端解析，不能在运行中读取可变的全局工具列表。
- 提醒增加列出、查看和删除能力，不开放手动添加；只有限定作用范围的工具可创建。保留 12 小时补发、过期状态、忙碌时延后和来源去重。
- 文件写入位置由后端控制，读取权限和路径范围也要明确；不能只限制输出目录就认为文件工具的范围已完整定义。
- 同一次 assistant 响应可以含 reasoning 与多个工具调用；保留原分组和调用 ID，不为简洁强制扁平化。容器结构按上述 Message 选择，本阶段不加入 token 流；协议附加字段白名单待供应商适配，终止使用通用 runner/interrupted 结果。
- 同一次响应中的工具按调用列表串行调度：sync 等执行完成，block-async 等交互完成，async 等可靠受理后即处理下一个调用，不等待最终交互结果。
- 不再区分 visible／hidden 工具，世界书工具也统一保留调用与结果。工具记录不成为可合成的台词；知识查询范围及注入条件仍由世界书配置保证。接口已移除 visibility 和隐藏通知分支。

2026-10-07 已完成 DeepSeek 真实协议实验：官方端点、deepseek-flash、ai 7.0.130、@ai-sdk/deepseek 3.0.61，两个无副作用工具提供 17、29。两次初始响应均为一个 assistant，包含 reasoning 与两个不同 ID 的调用；保留分组回传两份结果可得到 46。当前端点也接受拆开分组和倒序结果，但结果仍使用对应调用 ID；缺一个结果时 AI SDK 在 HTTP 前拒绝。7 次 HTTP 均成功，未验证流式、其他供应商、真正并发执行或停止后的取消结果负载。该实验不能证明只靠顺序即可重建协议。官方依据：[思考模式](https://api-docs.deepseek.com/zh-cn/guides/thinking_mode/)、[Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)。

### async 结果的合并与轮次分组

关联：RUN-04、RUN-06、TOOL-05、CHAT-02。2026-10-07 确认；字段已声明，内部调度尚未实现。

- 工具完成后立即登记结果。当前轮运行时先入队，不向正在运行的 Agent Loop 追加输入；空闲且允许受理新 Turn 时，取出当时全部已就绪的有效结果，合并为一条来源明确的 UserMessage，固定新 Turn 的输入。此后到达的结果留到下一批；没有有效结果时不创建空 Turn。
- 不等待同一次 assistant 响应或同一 Turn 发起的其他 async 工具，也不增加“所有问题回答完再提交”的限制。合并边界由下一轮受理时机自然形成；当前 Turn 已完整结束且允许受理时，先返回的结果可以先启动下一轮。只结束 Agent Loop、语音或演出仍未结束时继续排队。
- Conversation 在内存中记录轮次组：一条真正手动发送的用户消息发起的 Turn，与随后直到下一条手动消息之前的连续自动 Turn 属于同组。每个 Turn 保留自己的 UUID，组关系不替代 Turn 身份，也不要求另造一个轮次执行编号。
- 显式重生成是另一种开组操作：旧 Turn 终止后旧组保持失效，重生成的新 Turn 开启新组，新生成发起的 async 请求可以正常回流。即使重生成的输入来源是 async 结果，也按此规则开组；组关系由受理过程维护，不能仅根据存档中剩余 Turn 的相邻位置重新拼接，使已失效请求恢复资格。
- 组内任意 Turn 被 terminate，该组全部未消费的 async 结果失效。既清除已排队结果，也作废还未返回的请求；该组后续自动 Turn 发起的请求同样受此约束。取消决定不能因旧 Turn 从存档消失而遗忘；已经消费并进入历史的结果不因此删除，工具副作用不自动撤销。
- 新的手动消息被正式受理时，旧组所有未处理结果一律丢弃，尚未返回的请求也失效，不把旧结果并入新消息。点击工具中的回答／确认不算手动聊天消息；草稿变化、发送校验失败或忙碌拒绝也不关闭旧组。新组不受旧组迟到回调或停止命令影响。
- 原 async 工具向 LLM 返回的协议结果仍是 accepted；最终结果进入后续 Turn 的 UserMessage，不回写成原 tool_call 的第二份协议结果。批量内容保留有序结构化结果项，包含请求身份、来源 Turn／调用、状态及对应数据；问答能还原问题与答案的对应关系。给 LLM 的文本可以由这些项生成，裸字符串拼接不作为唯一权威记录。
- 请求身份用于去重；校验有效性、取出队列、消费结果、新 Turn 受理及用户发送／停止须串行协调。同一个完成结果至多纳入一个新 Turn。受理前失败不误判为已消费，受理后不能因通信重试重复启动新轮次。
- async 的最终失败或取消只结束对应请求，不进入自动回复队列、不触发新 Turn，也不补写原调用的第二份协议结果；同批其他成功且有效的结果仍可正常入队。可靠受理之前的失败仍作为当前工具调用的失败返回。
- 重启不恢复旧 async 队列、请求资格或轮次组，旧回调按状态未知拒收。提醒等内部事件在没有有效组时开启新组，不要求先有手动消息；持久化提醒仍按独立的到期和补发规则处理。
- 本阶段不增加跨 Turn 的自动续聊次数或累计预算，出现实际问题后再讨论；已有单轮执行与上下文预算保持原职责。长期提醒的保存、到期和补发仍独立处理，不因普通 async 结果失效而删除提醒。

### 世界书与诊断

关联：WORLD-01 至 WORLD-08。

- 世界书纳入后端设计，暂不实际调用，不设计本轮前端展示。开关、根包和进度属于 Chat；共享知识身份映射属于 Character。
- 上游解析本次允许的角色视角、依赖包与进度；直接上下文和世界书查询工具受同一范围约束，查询工具的启用仍由世界书配置控制。取消隐藏分类不取消查询权限。重新生成按当前设置重新解析，再固定本次执行。

- 读音覆盖的上游解析、世界书管理与内容制作保持此前暂缓／独立工具范围。

### 角色形态、换装与声音

关联：CHAR-01 至 CHAR-07、LIVE-06、TOOL-03、TTS-01 至 TTS-08。

- Character 使用 forms 集合和 defaultFormId；单形态角色也有一份 form，数量不固定为二。各 form 可有不同名称、描述、头像、主题色、声音配置与默认模型。
- 当前语义是同一角色采用一种形态并共享该 Chat 的历史；不据此承诺多个人格同时作为不同发言者。显式无效 form 报错，省略时使用默认形态。
- Chat 保存角色当前 formId 和每个形态独立的模型覆盖。更换服装不切换形态，也不修改 Character 的默认形态。默认模型使用 defaultModelId 指针；模型平级管理，迁移时登记旧默认模型。
- 换模型工具不改变当前 Agent Loop 的输出约定。Performance 按实际模型处理：V2 使用情绪动作组；V3 缺少或不能使用显式选择时按通道降级；下轮读取新目录。切换模型不重播台词音频。
- 上游按形态和情绪选出完整 VoiceProfile；Speech 不认识 Chat、剧情或全量 Character。参考材料依次降级到同形态默认材料、无声，不能静默换到另一形态。
- 语音重合成保留原台词、情绪、角色形态和发声语言／读音语义，采用当前对应声音资源与语音参数；不重新推断情绪。显式锁定参考材料的规则尚需细化。
- 语速、停顿和采样设置影响新任务；设备、精度、模型结构、并发及驻留预算下次启动生效。
- 语音开关按 Turn 开始时固定，运行中修改仅对下一个 Turn 生效，包括当前轮尚未生成的后续台词。关闭时 Conversation 不提交自动语音任务，直接将无音频台词标为 ready 交给 Performance；不隐式清除历史音频或补合成历史。
- Python 内部共享兼容的 BERT、HuBERT、SV 等公共模型；角色 GPT/SoVITS 网络、参考缓存、配置、取消和中间状态隔离。优先按同进程公共模型池及独立推理实例设计，公共模型按版本、设备、精度区分；随机状态、资源占用和卸载时机必须纳入内部约束。业务层保持任务接口，不承诺未经同条件测量的内存下降。

### 演出、输入与其他能力

关联：RUN-04、RUN-05、RUN-07、LIVE-04、LIVE-08、LIVE-10、INPUT-01 至 INPUT-07、APP-02、CHAT-08、CHAT-09、ASSET-01 至 ASSET-06。

- 停止保留正在播放的当前句；允许后台对话继续推进。整轮回放由 Conversation 把已保存角色台词变为临时 sequence，交给 Performance，不再生成或自动合成。
- transition guide 只有动作和表情，需要 slotId。普通 guide 正在播放时忽略新增；transition 播放时允许追加。普通队列空或普通队首未 ready 时执行过渡队首，recurring 队首持续重复，允许其阻塞后续过渡项。
- 普通队首 ready 时原子清除全部 transition，再执行普通内容；较后普通项 ready 不允许越过未 ready 的普通队首。stopTransitionGuide 清除所有过渡项，包括正在播放的。guideId 是稳定身份，不随插队或循环改变；循环结束回调以内部播放标识区分，只有最终完成、移除或关闭才结算等待。无有效动作或持续失败必须有界退出。
- 后台不实际循环过渡动作，普通内容仍按原后台规则推进；普通内容开始后清除已过时的 transition。BGM 是 Performance 的独立音轨，不进入台词队列。
- 背景、布局、朝向按 Chat 保存；BGM 按全局设置保存。
- 识别候选不覆盖新草稿；补充准备／唤醒状态和取消能力。语言规范化可暂缓，空或损坏音频的基本校验保留。
- 桌宠只绑定当前选中 Chat，主窗口与桌宠交接同一份 InputSessions 草稿；只有一个有效编辑入口。录音、识别、附件异步操作仍绑定开始时的 Chat。
- 导入缺失图片、音频或角色时保留可读历史及缺失引用，返回结构化警告；缺图在该消息的模型投影中说明不可读取，不伪造内容。损坏存档必须备份成功才可替换，其他 I/O 错误不一概当作损坏。
- 上传不增加 isRetry 参数，但保留作用域复用、并发合并及不确定结果处理。Live2D 包由独立导入模块完整处理并原子发布，平级模型不意味着包内必须摊平。
- 模型下载、资源编辑器、反馈、更新／修复、WebUI 接入保持独立模块或此前暂缓范围；世界书制作不进入发布程序。

### Python 行为复核后的补充选择

- 小剧场保留非连续生成：根据当前情景生成一次，之后只允许重新生成、不继续输入的限制由前端入口承担；后端不增加不可放宽的模式限制。情景进入 User Prompt，不以伪造用户文本解决空输入校验。正式声明采用 generateScenario(chatId, options)。
- 保留有限次数的格式修复；最终仍不合法时明确失败，不再把原始输出强行当作角色台词。原文如需保存只作诊断，不自动进入语音或正式回复上下文。
- 失败处理已确认：受理前失败保留提交材料，受理后失败保留输入、附件及已接受记录；只重试失败步骤，不重放工具副作用。保存失败保留内存状态并重试保存，不重新生成；语音失败保留文字并无声 ready。Agent Loop 不可恢复失败归 terminated，作废本组未消费 async 结果；单句语音／播放错误不终止整个组。
- 旧 Python 存档由独立导入适配器一次性转换：按用户输入边界初步划 Turn，不强求原响应分组；旧摘要移到其覆盖末条消息所属 Turn 的末尾，接受该轮尾部未概括内容从压缩上下文中丢失，原文仍保留，不强制重新摘要或启用压缩。形态缺失时使用对应角色默认形态并写入新记录；工具原始结果残缺可以接受，不追溯补全。新核心只消费新格式，不长期保留旧存档兼容转换方法。
- 正常 Turn 的 finished 表示生成、该轮自动语音和演出全部完成或已按错误规则结算；仅剩本轮播放时也拒绝下一轮提交，包括 async 自动新轮次。待返回 async 交互、BGM、循环过渡动作不计入完成条件；历史回放或独立重合成不让已完成的 Turn 重新 running。运行态仍由 Conversation 内存维护。
- 历史回放不阻止新 Turn。新轮次通过校验和持久化受理后，由 Conversation 协调 Performance 停止对应的临时回放 sequence，包含当前播放句及待播内容，再交接新轮演出；提交被拒绝时不打断回放。手动与 async 新 Turn 使用相同规则。只清理相关回放，不关闭常驻对话 sequence，不终止回放来源的历史 Turn 或使其轮次组失效；回放的迟到回调不能干扰新演出。普通未完成 Turn 的播放仍锁住新提交。
- 保存失败时保留该 Chat 的内存内容并暂停受理新生成和历史修改；允许查看、停止和重试保存，保存恢复后解除限制。已经运行的任务仍需正常结算和保留其结果，保存错误不隐式重放模型或工具，不锁住其他 Chat。
- 重启恢复相当于旧执行已经中断：只恢复已保存内容，不自动续跑 Agent Loop、重放工具、恢复未完成交互或演出。对已保存但缺少结果的工具调用按通用中断结果处理，不推定外部副作用未发生；未落盘内容不保证恢复。新核心不需要为此持久化 running 映射。
- 具体案例及停止后的衔接建议见 [二次复核](python-core-design-review.md)。其中标为建议的处理还未定案。

## 仍待讨论的问题

- 忙碌互斥：普通 Turn 完整结束前锁住新提交，历史回放则由新 Turn 受理时中断；保存失败阻止新生成及历史修改。仍需细化停止普通 Turn 后保留当前句时的提交时机，以及手动语音重合成的目标句保护。
