# 数据目录与统一资源访问设计

确认日期：2026-10-14。实现更新：2026-10-24。多目录注入、统一资源访问、引用生命周期及聊天旧版本清理已接入，具体范围和兼容限制见文末。

第一阶段只拆分可写目录的注入，并由资源模块统一管理不同位置的资源。目录选择界面、迁移、容量查看和选择清理均暂缓，不为这些功能提前增加后端入口。

## 数据分类

目录归属按用途和保留要求决定，不按单个文件大小或扩展名决定。

| 类别             | 内容                                                                                 | 保留约定                                                   |
| ---------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| 应用数据         | 设置、角色与对话身份定义、聊天文本、资源登记信息、聊天图片                           | 长期保留，本阶段不提供应用内清理功能                       |
| 资源库           | 所有大型模型，包括 GPT-SoVITS、Embedding、Reranker 等模型；Live2D 模型包；保留的音频 | 独立于安装包和应用数据，可放在其他磁盘；选择清理后续再做   |
| 缓存与临时文件   | 实际需要的下载中间文件、文件交接暂存、可丢弃的派生文件及运行日志                     | 不作为用户数据的唯一保存位置；不新增缓存管理或自动清理功能 |
| 随程序发布的文件 | 程序代码、固定提示词模板、图标及其他内置文件                                         | 随安装包发布，运行时只读                                   |

设置缺失时使用默认值，但设置文件损坏不能直接当成首次启动并覆盖。默认值属于程序，用户保存的设置属于应用数据。

聊天图片缺失会影响历史展示，也可能改变后续模型请求的输入，因此与聊天文本一起作为应用数据保留。角色头像、对话身份快照头像同样按应用数据保留。未来至多另行设计聊天图片清理，不将整个应用数据目录纳入通用清理。

保留的音频放入资源库。历史回复音频缺失时，仍保留原台词和资源引用，回放可提示不可用并保留文本展示；不能因此删除台词。此规则不代表所有音频缺失都可忽略：若某项操作必须读取输入音频或参考音频，应按该操作的要求报告资源不可用。

Live2D 模型包作为整体放入资源库，包括模型文件、贴图、动作和表情文件，保持包内相对关系。不能因为贴图是图片，就把它拆到聊天图片目录。

当前不为尚未接入的推理缓存或可重建索引建立新实现。现有语音链路有 `speech-temp` 输出，再将需要保留的音频导入资源系统；这类文件交接可使用临时目录，不等于需要新增一套推理结果缓存。未来若产生可重建索引，再按实际需求接入；原始资料和用户修改不能归入缓存。

## 目录由宿主注入

宿主负责解析操作系统默认位置和启动配置。后端不导入 Electron，也不自行猜测当前工作目录或安装目录。

使用以下三个具名根目录，避免多个含义不同的参数都叫 `dataRoot`：

| 装配参数              | 用途                 | 使用者                                                         |
| --------------------- | -------------------- | -------------------------------------------------------------- |
| `appDataRoot`         | 应用数据根目录       | 设置、角色目录、聊天存储，以及资源模块的登记信息与应用数据资源 |
| `resourceLibraryRoot` | 资源库根目录         | 资源模块及经装配授权的模型运行适配器                           |
| `cacheRoot`           | 缓存与临时文件根目录 | 资源模块、下载或语音文件交接，以及宿主管理的日志输出           |

三个目录分别注入，不能在后端中强制把资源库和缓存拼接到应用数据目录下。宿主可以让它们位于同一磁盘，也可以分别放置。第一阶段采用启动时确定的目录，运行期间不切换。

装配层只把需要的目录或资源访问能力交给相应模块，不把完整目录配置传遍业务层：

- `Settings`、`CharacterCatalog`、`ChatStore` 各自获得应用数据下的存储位置，继续管理自己的结构化数据。
- `MediaAssets` 获得三个位置的资源存储配置，统一登记、导入和解析资源。
- `Conversations`、`Agent` 等通过资源模块访问文件，不拼接磁盘路径。
- Python 语音的进程装配获得实际需要的模型位置和临时输出位置；角色权重、参考音频等仍由资源模块解析。

示意布局如下。子目录名称属于实现细节，不进入业务契约：

```text
appDataRoot/
  settings.json
  characters.json
  personas/
  chats/
  assets/
    index.json       # 三类位置的统一资源登记与持有关系
    files/           # 聊天图片、头像等应用数据资源

resourceLibraryRoot/
  models/
  live2d/
  audio/

cacheRoot/
  assets/
  speech-temp/
  logs/
```

macOS 应用数据默认位于当前用户的 `~/Library/Application Support/<应用目录>/`；Windows 采用 `%LOCALAPPDATA%\<应用目录>\`。Electron 的 `userData` 在 Windows 上默认基于 `%APPDATA%`，因此采用 LocalAppData 需要宿主明确解析，不能把两者视为同一目录。资源库提供独立的宿主配置位置，本阶段不实现目录选择界面。开发环境可以继续使用项目内的 `.local` 子目录，并与正式数据隔离。

操作系统目录应通过相应能力解析，不硬编码用户名、盘符或应用安装位置。参见 [Electron 路径说明](https://www.electronjs.org/docs/latest/api/app#appgetpathname)和 [Windows 已知目录定义](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid)。

## 统一资源描述与访问

应用数据、资源库和缓存中的受管理资源共用一套 `AssetRef`。业务持久化仍只保存稳定的资源 ID，不增加绝对路径、盘符、目录类别或临时 URL。

资源模块内部登记资源的用途、所在位置类别、相对位置和必要元数据。统一登记信息保存在应用数据中，不为三个目录分别建立互不关联的资源身份与持有关系。外部资源库暂时不可用时，应用仍能读取登记信息和聊天文本。

这种统一针对资源文件，不要求把设置 JSON、聊天 JSON 和日志也包装成 `AssetRef`。它们仍由各自负责的模块管理。

### 写入时表达用途，读取时只使用引用

写入方需要说明资源用途，例如聊天图片、头像、模型包、保留音频或临时材料。资源模块根据统一规则决定写入位置；写入方不选择盘符或子目录。

用途应来自可信业务操作，不能只依赖扩展名、MIME 类型或任意客户端传入的目录类别。选择一个文件只确定来源，不足以确定它应该放在哪里；导入操作需结合本次用途完成登记。

读取方使用相同的资源访问能力，无需判断资源属于哪个根目录：

- 聊天保存图片和音频的 `AssetRef`，不保存两种目录路径。
- Agent 通过资源模块读取聊天图片，不自行寻找图片目录。
- 前端通过已授权的资源访问地址展示图片或播放音频，不接收本机路径。
- 模型加载需要本地文件时，由可信适配器向资源模块解析路径；普通业务模块仍只传资源引用。

对路径透明不代表抹平资源用途和不可用状态。资源模块负责定位与访问，业务模块根据明确的资源错误决定本次操作能否继续。

### 模型文件与本地路径

模型加载器可能需要真实文件路径或完整目录。资源模块应提供受限的本地解析能力，避免为了统一读取而把大型模型整体读入 Node 内存。Live2D 整包解析需保持入口文件和包内相对关系。

本地解析与文件访问授权只留在可信宿主和运行适配器之间，不能开放为客户端任意读写路径的入口。Python 对文件访问位置的校验应与宿主注入的目录一致，不能继续假设全部角色资源都在 `dataRoot/assets`。

### 持有关系与缺失处理

`AssetOwnerId` 继续表示草稿、存档或任务对资源的持有关系；物理目录分类不替代持有关系。资源交接仍先建立接收方引用，再释放发送方引用。

需要长期保留的资源必须在提交持久引用前存入对应的应用数据或资源库位置，不能让存档唯一依赖缓存文件。临时文件可以由任务持有；是否需要登记为资源取决于它是否需要跨模块交付，不要求给每个工作文件分配 ID。

资源登记成功不等于文件始终可用。文件丢失或资源库不可访问时，读取应明确失败，保留登记信息和原引用，不返回伪造的空内容，不自动改写聊天，也不悄悄切换到另一个根目录。

聊天内容与资源不在同一目录，不影响统一读取或归档枚举：这些操作按资源引用访问资源模块，不能依靠递归复制聊天目录来收集所有附件。完整归档规则沿用原有设计，本次不扩展导出功能。

## 安装包只读

macOS 正式发布采用标准 `.app` 应用包。运行时不在包内保存设置、聊天、模型下载、日志或临时文件，也不修改包内程序和模板。程序升级以安装包更新处理，不通过业务运行逻辑原地编辑自身。

随程序发布文件是独立的只读来源，不是第四个可写数据根目录。固定提示词模板继续由 Agent 按[现有设计](nunjucks-prompts.md)加载，不为了统一用户资源而改成可编辑的 `AssetRef`。

## 当前实现与第一阶段范围

[装配入口](../src/backend/create-core-backend.js)现在接收三个独立根目录。`MediaAssets` 在应用数据的 `assets/index.json` 保存版本 3 索引，公开元数据包含用途与文件/目录类型，内部位置另存，不进入 `AssetRef`。[Electron 宿主](../src/main/index.js)将三个位置分别交给后端与语音进程，并在 ready 前把 Chromium 会话目录设为 `cacheRoot/chromium`。

第一阶段已完成：

1. 宿主解析并注入三个具名根目录，各模块仅取得自己需要的目录或能力。
2. 资源模块以统一登记信息描述三个位置，按用途路由写入，按 `AssetRef` 解析读取。
3. 将聊天图片与头像放入应用数据，将大型模型、Live2D 包和保留音频放入资源库，将实际临时输出放入缓存目录。
4. 调整语音等实际接入点，消除对单一 `dataRoot/assets` 的假设，并保证安装包运行时只读。

目录迁移、运行中切换、容量统计、资源管理页面、选择清理、聊天图片清理、缓存配额与自动清理、外部模型原地挂载均暂缓。已有 `collectUnused` 不能因为新增目录分类就自动接入或扩大清理范围；应用数据资源不得被通用缓存清理连带删除。保留引用交接和失败写入回滚，不等于实现产品清理功能。

### 启动配置与兼容限制

- `DSAKIKO_DATA_DIR` 对应应用数据，`DSAKIKO_RESOURCE_LIBRARY_DIR` 对应资源库，`DSAKIKO_CACHE_DIR` 对应缓存。开发默认值分别为 `.local/core-v1`、`.local/library`、`.local/cache`。三个根目录不得重叠，打包后的宿主拒绝与安装包重叠的可写位置。
- 旧 `DSAKIKO_RESOURCE_ROOT` 已停用，残留配置会明确阻止启动，提示更新配置；不悄悄改用另一处基础模型。基础模型需准备在资源库的 `models/GPT_SoVITS/pretrained_models`，G2PW 资源保留其相邻布局。
- 旧单目录索引与损坏索引均明确拒绝，不当成空索引覆盖；没有兼容迁移工具。测试新布局时应使用新的应用数据目录，保留原数据。
- 资源导入要求显式 `purpose`：`chat-image`、`avatar`、`attachment` 属于应用数据；`model`、`live2d`、`audio` 属于资源库；`archive`、`temporary` 属于缓存。`temporary` 仅供后端创建。一般附件按应用数据保留，避免未知类型误入缓存。
- 模型目录支持完整复制与包内文件读取，拒绝符号链接和路径越界。本阶段不实现 ZIP 解包、Live2D 配置生成或外部模型原地挂载。
- 聊天归档使用版本 2，记录资源用途并在导入时恢复对应位置；旧版本 1 归档明确拒绝。本阶段归档仍只支持文件资源，包含模型目录时明确报不支持，不只导出入口文件而丢掉其余文件。
- `collectUnused` 暂停执行并明确返回 `cleanup_unavailable`，不加入新的清理入口或自动任务。引用租约到期仅释放 owner，不删除音频等资源文件。
- Python 代码作为只读资源打包到 `.app/Contents/Resources/python`，运行时使用缓存工作目录并关闭字节码写入；解释器和依赖仍需单独准备。

以上目录拆分不包含迁移。下面的聊天版本维护会删除受控存档目录中的旧 revision 文件，但不删除媒体资源文件。

实现验收关注：三个根目录可以分别指定；同一 Chat 的图片和音频可分别落盘并通过统一引用读取；持久引用不依赖缓存；资源缺失保留文本与引用；模型包结构完整；业务层不拼接资源路径；运行时不写安装包。

## 引用生命周期与聊天版本清理

资源需要保留，可能是因为用户把它放进了资源库，也可能是角色、聊天或运行任务正在使用。同一个资源可以同时有多个 owner，释放其中一个不影响其他引用。所有引用变更都在 MediaAssets 的同一队列内读取和保存索引，不要求调用方先读取旧集合。

`extractAssetReferences(value)` 是纯函数，只识别项目约定中仅含 `id` 的 AssetRef 对象并去重，不查询索引或文件。增删接口适合草稿和任务，完整替换适合持久保存。例如同一图片出现在两条消息中，删除一条后从剩余聊天重新提取引用，仍会保留该图片。

```js
await assets.addReferences(owner, [image.asset, audio.asset])
await assets.removeReferences(owner, [image.asset])
await assets.replaceReferences(owner, extractAssetReferences(snapshot))
await assets.releaseOwner(owner)
```

| 持有者                       | 保留与释放规则                                                                             |
| ---------------------------- | ------------------------------------------------------------------------------------------ |
| library                      | 用户主动导入的模型长期保留；分配给角色不释放。明确移除库条目才释放库引用。                 |
| character、persona、settings | 从已保存内容维护完整引用；更换或删除配置提交后更新。BGM 关闭但配置仍保留时，继续持有音频。 |
| chat                         | 只持有当前已提交聊天，创建、分支、归档导入和损坏恢复共用 ChatStore 提交流程。              |
| pending                      | 写业务文件前保护新引用；根据已提交内容完成正式引用交接后移除。                             |
| draft                        | 附件导入时建立；已保存目标接手后释放对应引用，放弃草稿时释放全部。                         |
| chat-memory、turn            | 保护内存内容及本轮冻结材料；保存失败时继续保留，聊天关闭或执行结束后释放。                 |
| speech-input、speech         | 输入保留到真实任务终态，输出保留到接收方建立引用或明确废弃；取消等待不代表任务结束。       |
| speech-model                 | Python 没有逐模型卸载通知，同一进程、同一组权重只建立一份驻留引用，保守保留到进程退出。    |
| import、export               | 导入期间保护输入与产物；导出读取期间保护源资源，生成的独立归档另有十分钟保留期。           |
| use、scene、guide、access    | 分别保护异步读取、场景、演出音频和客户端访问，实际操作结束后释放。                         |

持久保存通过 `commitReferences` 完成：先写 pending 引用与提交日志，再执行业务提交，最后读取权威持久数据，更新正式 owner 并清除日志。业务数据发布后若引用收尾失败，保存仍返回成功，保护日志继续存在。后台维护或下次启动会重试交接；提交失败也按磁盘事实处理，不能假定业务文件尚未发布。维护错误保存在 `assets.maintenanceProblems`，不冒充业务保存失败。

启动恢复只处理提交日志记录的目标，不扫描旧业务数据补建引用。索引版本提升为 3，增加 `temporaryOwners` 和 `commits`；旧版本索引明确拒绝，不自动迁移。临时 owner 记录后端会话，重启后释放上次运行的普通临时引用。语音输入和模型还记录宿主确认的子进程 PID：宿主异常退出后子进程若仍存活，引用继续保留；检查权限不足或 PID 重用时也保守保留。

### 草稿与访问调用

正式 HTTP 客户端通过 `assets.createDraft()` 获得 draftId。普通附件上传必须提供 draftId，本地宿主导入通过 `importFiles({ purpose, draftId })` 传递同一身份。模型可以直接进入资源库；即使先放入草稿，主动导入的模型也会建立独立 library 引用。导入结果的 libraryItemId 用于明确移除库条目，`listLibraryItems()` 可查询现有条目。

```js
const { draftId } = await client.assets.createDraft()
const image = await client.assets.upload({
  draftId,
  name: 'picture.png',
  mediaType: 'image/png',
  base64: imageBase64,
  purpose: 'chat-image'
})
// 将 image.asset 写入业务内容，等待保存或聊天受理成功后再交接。
await client.assets.commitDraft(draftId, { kind: 'chat', id: chatId })
// 用户放弃尚未提交的编辑时调用：
await client.assets.discardDraft(draftId)
```

`commitDraft` 只释放已由指定目标正式持有的资源，未交接附件继续留在草稿中；它不能替代业务保存。草稿三十分钟过期，访问凭证五分钟过期，正式客户端每分钟续期其活动草稿和访问。使用者在播放结束、停止或模型实例卸载后调用 `releaseAccess(leaseId)`；客户端关闭时释放全部已登记访问和草稿，异常断开以租约过期兜底。HTTP 文件读取另有 use owner，访问凭证释放不会提前结束实际读取。

正式音频输出已接入结束、停止、换曲、失败和迟到访问的释放，后端场景与 guide 也分别持有资源。现有旧 IPC 页面原型没有在本次改造成正式 HTTP 页面；后续页面和 Live2D 渲染器应使用上述约定，不直接修改任意 owner。InputSessions 的录音、识别及完整编辑 UI、RemoteFiles 和 Live2D 压缩包导入器仍不在本次实现范围。

### 聊天只保留当前版本

聊天位于 `<appDataRoot>/chats/`。每次保存先写 `<chatId>.<revision>.json`，再原子替换 index.json；索引发布成功后才删除旧 revision。读取、导出和清理共用存储队列，旧文件不会在读取中途消失。删除聊天先提交索引删除，再清理文件。

保存成功后及时清理，启动时兜底清理中断留下的旧版本与受控临时写入文件，不增加定期扫描聊天目录的任务。只识别存储模块产生的文件名，不删除目录、符号链接、未知文件或 `.backup`。清理失败记录诊断，后续保存或启动重试，不把成功保存改成失败。旧 revision 没有长期资源 owner，损坏备份也不承诺媒体完整可恢复。

这会避免磁盘长期积累聊天完整副本，但每次保存仍需序列化并写入完整聊天，未改为增量存储。
