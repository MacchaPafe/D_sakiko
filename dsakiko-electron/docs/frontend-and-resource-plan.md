# Electron 前端重写与资源管理初步规划

整理日期：2026-10-29。

这一轮准备重写旧的前端 demo，以角色陪伴为中心，先完成一个主窗口。Electron 和 WebUI 尽量共用同一套前端、交互和业务逻辑。先一起讨论布局与样式，把有用的操作和状态做完整，再由用户或其他模型继续美化。

下面记录已经确定的使用方式和建议的实现顺序。这些是接下来的工作，不代表目前已经实现。

## 现有基础怎么接着用

目前正式后端已经通过 HTTP 提供业务调用，通过 WebSocket 推送状态快照；前端已有共用客户端。Electron 主进程负责启动后端，preload 只提供连接信息、运行环境和本地文件导入等少量桌面能力。旧 demo 的部分通信方式已经失效，重写时应接正式客户端。

新的前端可以按下面的职责拆开：

- 页面和组件负责布局、输入、状态展示及舞台渲染。
- 页面控制逻辑负责当前角色、聊天选择、草稿、订阅及本地播放。
- 共用客户端负责业务请求、状态同步及资源访问。
- 宿主适配负责 Electron 和浏览器的差别，例如文件选择、连接凭证和窗口可见性。

后端继续负责角色、聊天、生成、存档和资源管理。窗口隐藏、页面切换或浏览器断开，不等于取消后端任务。WebUI 操作的资源库在后端所在的机器上，浏览器本身不负责安装 Python 或管理服务端磁盘。

相关基础见 [架构说明](architecture.md)和[数据目录与资源设计](data-directories-and-resources.md)。

## 主窗口如何使用

舞台是陪伴页的主体，聊天记录默认收起。舞台显示角色当前正在说的话，空闲时保留最后一句回复。展开记录只是改变布局，不重新加载角色或重新开始播放。

目前可行的页面布局以“陪伴与记录并列”为参考：左侧放角色与聊天导航，中间是主要舞台，右侧是可展开的聊天记录，主内容区底部保留共用输入区。默认收起右侧记录，让舞台获得更多空间；需要阅读历史时再展开，与舞台并列显示。两种状态使用同一套页面和播放逻辑。这里先确定区域关系，具体比例、配色和控件样式后续再调整。

侧边栏用选项卡切换“单人对话”和“小剧场”：单人对话先显示角色头像，再展开该角色的聊天；小剧场直接按剧场组织。

| 用户操作 | 界面行为 |
| --- | --- |
| 点击已有聊天的角色 | 展开她的聊天列表，收起其他角色，进入上次访问的聊天 |
| 点击没有聊天的角色 | 显示正常舞台和输入框，此时还没有聊天记录 |
| 在这个空白界面首次发送 | 自动创建聊天、提交消息，并在侧边栏增加一条聊天 |
| 删除当前聊天 | 回到同角色的空白界面，即使她还有其他聊天也不自动跳过去 |
| 切换聊天 | 停止旧聊天的本地播放，跟随新聊天的演出 |
| 切到其他页面，再返回 | 离开时暂停本地播放，返回时跟随最新状态，不自动补播遗漏内容 |

因此，前端必须支持“已选择角色，但尚无聊天”的状态。角色展示不能依赖 chatId；首次发送前也可以持有草稿和附件。上次访问的聊天已经不存在时，回到同角色的空白界面。

首次发送建议由后端提供一次可去重的“创建并受理”操作，避免双击或网络重试创建多个聊天。受理前失败保留草稿；受理成功后即使生成失败，也保留这条聊天和失败状态。这里不用等待整轮模型生成完成才保存聊天。

聊天记录随已确认的内容更新，可以比舞台提前；舞台字幕跟随本地演出。这两种进度要分开，切换聊天时也不能残留上一位角色的声音或字幕。历史内容需要回放时，由用户明确操作；本轮不增加返回页面后自动补播的能力。

只做一个主窗口。关闭按钮隐藏窗口，托盘可以重新打开；macOS 点击 Dock 图标也恢复这个窗口。隐藏或最小化时暂停本地播放，单纯失去焦点不暂停。明确选择“退出”时才关闭后端和子进程。

## 先把哪些界面内容做完整

先画一版包含侧边栏、舞台、字幕、输入区和可展开记录的主窗口，再逐项接业务。输入区需要有发送、停止、附件和语音识别入口；页面还要能说明连接中、生成中、资源准备中及失败的原因。具体尺寸、配色、按钮位置和设置页面布局仍可以继续讨论。

每个组件都准备正常、空白、加载、失败和不可用等实际会遇到的状态。界面组件尽量只接收展示数据和操作回调，复杂业务不藏在样式组件里。这样后续调整布局与视觉时可以保留业务逻辑，减少重写。

## 可选资源如何提供

后端维护资源清单，记录用途、版本、平台、来源、大小、校验信息及当前是否可用。前端按功能解释这些资源：例如第一次使用角色语音时，说明需要下载什么、大致占多少空间、保存在哪里，再让用户决定。首次使用页面也可以介绍这些功能，但不一次抛出内部文件清单。

| 内容 | 提供方式 |
| --- | --- |
| Pixi、Live2D 相关运行库 | 随程序打包，不要求移到资源库 |
| 爱音、素世、祥子的预置人设与 Live2D 资源 | 随程序附带；无角色时用于初始化，资源复制到外置库，角色定义按现有应用数据规则保存 |
| GPT-SoVITS Python 源代码 | 随程序打包 |
| Python 解释器、依赖环境、语音基础模型及角色语音权重 | 按需准备到外置资源库，按平台区分 |
| ASR | 支持库预置，识别模型按需下载 |
| 后续 embedding 等模型 | 沿用通用资源流程，具体接入时再补清单 |

预置角色初始化需要可以安全重试，不能覆盖已有角色和用户修改。约 20 MB 的体积是目前估计，实际打包时再核对。

没有语音或识别资源，也能使用文字聊天和舞台。角色本身没有 Live2D 模型时，保留背景、角色信息及字幕，不把整个陪伴页变成错误页。模型调用需要的连接配置单独处理。

通用下载器暂定使用 [ipull](https://github.com/ido-pluto/ipull)，接在 Node 后端，供 Electron 和 WebUI 共用。它支持单个文件的多连接分片下载、暂停恢复、重试和进度统计。实际速度仍取决于下载源；实现时需要验证 Range 支持、重定向、链接过期、进程重启后续传及远端文件变化等情况，不能把分片下载等同于差分更新。

下载任务由后端持有。关闭下载对话框或隐藏窗口不会取消任务；前端可以重新查看进度、取消或重试。文件先下载到临时位置，校验完成后再启用；失败或取消不能留下看似可用的半成品。完成后还要登记资源引用并绑定到对应功能，不能只把文件下载下来就算完成。

Python 环境还需要单独的安装与可用性检查，不能把“下载完成”当作“语音已可使用”。下载器可以共用，文件模型和运行环境的安装步骤分别实现。

## 主程序如何更新

主程序提供统一的检查、下载、安装及失败提示，底层按平台选择更新工具。主程序更新与模型、Python 环境等可选组件更新分别管理；修复一个模型或语音环境，不要求重新下载整个 Electron 安装包。

| 平台 | 更新方向 |
| --- | --- |
| Windows | 继续使用 electron-builder 的 NSIS 安装器，接入 electron-updater；允许分发未做 Authenticode 签名的程序和安装包 |
| macOS | 使用 Sparkle，通过 Electron 桥接接入；允许使用 ad-hoc 应用签名，不以购买 Apple Developer 证书为前提 |

macOS 的应用签名和更新包签名分别处理。没有 Developer ID 和公证时，首次下载仍可能需要用户在系统设置中允许打开，Sparkle 不能消除 Gatekeeper 限制。更新包使用 Sparkle 的 Ed25519 签名，自行生成密钥并在应用中保存公钥，不需要购买证书。具体 Electron 桥接库尚待打包验证，重点检查原生模块、签名顺序、两个 ad-hoc 版本之间的更新和重启。参见 [Sparkle 说明](https://sparkle-project.org/documentation/)及桥接候选 [electron-sparkle-updater](https://github.com/Innei/electron-sparkle-updater)、[electron-sparkle](https://github.com/biw/electron-sparkle)。

Windows 按当前 electron-builder 26.x 的配置处理未签名更新包；需要时关闭 `win.verifyUpdateCodeSignature`，不照搬新版文档的配置。未做 Authenticode 签名不代表关闭更新来源验证，发布清单与安装包仍需通过应用信任的发布密钥验证，不能只依赖与下载文件一起提供的哈希值。系统仍可能显示未知发布者或 SmartScreen 提示。参见 [26.x Windows 配置](https://www.electron.build/v26/docs/win/)。

安装前需要结束相关后端和子进程，再由更新工具替换程序并重新启动。正式接入时验证更新失败、中断恢复、Windows 文件占用和旧版本升级；当前只确定工具与分发方向，不承诺已经具备这些能力。

## Python 环境如何准备和更新

正式版采用预制环境负责首次安装，锁定依赖清单和独立依赖产物负责后续更新。这里的预制环境是普通 Python 解释器及其依赖，不是把服务冻结成单个可执行文件；预制不要求以后每次都重新下载整个环境包。

发布时按操作系统、CPU 架构和推理后端准备环境，使用固定且经过验证的 Python、Torch 及其他依赖版本。Windows CPU、CUDA 和 macOS 各架构分别验证，不直接选择最新 Python，也不要求用户安装编译器。项目代码继续兼容 Python 3.9，实际分发的解释器在现有依赖支持范围内确定。

解释器可以使用 python-build-standalone 等独立分发，依赖在对应平台准备；缺少可用 wheel 的包在发布阶段构建。不能直接压缩开发机的 `.venv` 就认为可以分发，需要在不同目录和干净机器上验证路径、动态库、关键模块导入及实际合成。普通虚拟环境需要在最终版本目录创建，避免准备完成后搬动路径。

uv 用于环境构建、依赖同步和修复，可以按平台作为私有工具附带或随环境提供，通过绝对路径调用，不要求用户全局安装或修改 PATH。首次安装优先由 ipull 下载预制环境包，完成校验、解压和可用性检查后登记。运行时直接启动已选环境中的 Python，沿用现有独立语音服务，不在每次合成前自动同步依赖。

后续可以只新增或更新发生变化的 Python 包，复用未变的依赖和可用缓存。一次小更新也可能引起传递依赖变化；涉及 Python、Torch 或推理后端变更时，仍可能需要较大的下载。预制包解压出来的依赖不会自动成为 uv 的 wheel 缓存，减少重复下载所需的依赖产物、缓存和复用方式需要在发布流程中明确提供。

更新发布的是目标环境的完整锁定清单、固定包源和校验信息，由本地安装器生成同步操作，不以连续执行历史上的 `pip install -U` 指令作为版本定义。这样新用户可以直接安装目标版本，已有用户可以增量同步，安装中断后也能依据同一目标重新检查。先支持有限的环境准备和依赖同步操作，不增加通用的远程脚本执行机制。参见 [uv 锁定与同步](https://docs.astral.sh/uv/concepts/projects/sync/)及[缓存说明](https://docs.astral.sh/uv/concepts/cache/)。

下载增量与启用方式分开。优先在独立版本目录准备候选环境，验证依赖导入、设备可用性和短句合成后，等待当前语音任务结束，停止服务和 worker，再切换环境并重启。更新失败继续使用旧环境，不原地修改正在运行的环境。通常不需要重启整个 Electron 应用；清理旧版本前确认没有进程继续使用，并为旧环境、候选环境、下载包和缓存同时存在预留空间。

## 可选组件如何分别更新

模型和 Python 环境从首次接入时就保留独立身份、版本及安装状态，不把应用版本号当作所有资源的版本。组件清单记录平台、推理后端、来源、大小、校验信息和兼容条件；本地分别记录已安装版本、当前启用版本及准备结果，不能因为目标目录存在就认为更新成功。

| 管理对象 | 版本与更新边界 |
| --- | --- |
| Python 环境 | 以解释器、平台、推理后端和完整依赖锁定清单描述一个环境版本，支持后续包级更新 |
| GPT-SoVITS 基础模型 | 独立模型包版本，声明支持的引擎与模型格式，按需更新 |
| 角色语音权重及其他导入模型 | 保留原资源身份和引用；官方组件更新不覆盖用户导入的文件 |
| ASR 模型 | 独立模型版本，声明格式及支持的识别运行库 |
| GPT-SoVITS 服务代码、ASR 支持代码 | 初期继续随主程序发布，记录兼容接口；以后确有需要时再增加外置代码加载和独立发布 |

独立发布不代表任意版本都能组合。每项功能需要描述经过验证的服务代码、环境和模型组合，并声明宿主接口兼容范围。例如一次角色语音更新可以只更换两个依赖，保留原模型；只有新环境与当前代码、模型兼容时才启用。Python 包自身的版本由环境锁定清单管理，不把每个包都做成面向用户的可选组件。

下载、准备、验证和启用分别记录。准备失败时保留当前可用版本，中断后可以检查并重试；需要一起变化的代码、环境和模型按兼容组合启用，不能先切换其中一项而留下不可用状态。发布清单需要验证发布来源，文件需要校验内容。资源登记及 AssetRef 仍沿用现有规则，组件版本记录不替代资源引用和持有关系。

前端按功能展示是否有更新、所需下载量、是否暂时影响使用及失败后的重试入口，不要求用户选择单个 Python 包。先实现模型和环境的独立发布、兼容检查与可靠切换；支持代码完全脱离主程序更新，需要另行确定加载位置和接口边界，不在本轮直接实现。

## 资源保存在哪里

Windows 按用户希望，优先把大型资源放在用户选择的程序位置，不固定塞进 C 盘的 LocalAppData。macOS 默认继续使用 Application Support 下的外置资源库。应用数据、资源库和缓存仍分别管理，业务引用继续使用 AssetRef，不保存盘符或绝对路径。

Windows 已确认按下面的布局继续设计，具体安装器实现与验证尚待完成：

```text
D:\D_Sakiko\          用户选择的总目录，盘符只是举例
  启动入口             指向 app 内主程序的薄启动器，名称待定
  app\                程序文件，安装器管理的应用目录
  library\            模型、Live2D、语音环境及保留的音频
  cache\              下载临时文件、安装暂存及运行缓存
```

从用户角度，程序与大资源仍放在一起，总目录提供启动入口，不必先进入 app。优先增加只负责启动 app 内主程序的薄启动器，保持 Electron 文件仍在 app 内，不为打开程序方便而把所有程序文件移到总目录。具体入口名称和打包方式在安装器验证时确定。

安装器的实际安装目录限定为 app，library 和 cache 与它同级；总目录中的启动入口单独按受管理文件创建、替换和卸载，不递归清理整个 D_Sakiko 总目录。启动器保持职责简单，业务配置和子进程生命周期仍由主程序管理。资源库保留独立选址能力，不要求始终与程序在同一磁盘。

当前项目使用 electron-builder 26.15.3 的 NSIS 安装器，尚未定制这些规则。其默认卸载脚本会递归清理安装目录，升级也会执行旧版本的卸载流程。因此，“新安装包不包含 library”不能保证它被保留；需要落实上面的目录边界，并实际验证从旧版本升级及卸载后资源仍然保留。新脚本也不能改变已经安装的旧卸载器行为，旧目录迁移需要单独验证。参见 [26.x NSIS 安装器说明](https://www.electron.build/v26/docs/nsis/)及本地依赖中的 `app-builder-lib/templates/nsis/uninstaller.nsh`。

首次下载大资源时显示目标位置和所需空间，并允许另选资源库。路径不可写时要求换到可写位置，不静默转回 C 盘。下载包、解压暂存和 Python 包安装缓存也要使用选定磁盘，否则最终模型在 D 盘，安装过程仍可能占满 C 盘。uv 的解释器安装位置、下载缓存、包缓存和安装子进程的临时目录都要显式配置。空间检查要考虑下载包、解压结果及更新前后环境短暂共存。

卸载默认保留资源库，删除资源应是明确的单独操作。角色、聊天等应用数据继续沿用现有独立目录规则；其中的聊天图片也可能增长，不能把它们当作可随便清理的缓存。整库迁移的界面和流程可以随后补充，不阻塞首次选择位置。

## 旧版本导入与实现顺序

旧版导入要覆盖基础模型、角色的 Live2D／人设／语音模型，以及聊天记录。先扫描旧目录，展示可导入内容和缺失项，再导入并建立新系统中的引用；保留旧版原文件，重复导入应能识别已有内容。

文件复制先保证可靠。可以在支持的文件系统上使用写入时分离的文件克隆来节约空间；硬链接只考虑明确不会原地修改的模型文件，并检查同盘、权限和更新方式，不直接用于整个旧数据目录。下载和旧版导入最终都应走相同的校验、资源登记及功能绑定过程。

建议按下面的顺序推进：

1. **画出主窗口和关键状态。** 确定所有必要输入与状态元素，并整理页面需要的后端接口；同时检查旧版数据样本，避免导入需求到最后才暴露。
2. **打通文字陪伴。** 接正式客户端，实现角色导航、空白界面、首次发送、聊天切换与删除，以及记录展开／收起。
3. **接舞台和桌面生命周期。** 完成字幕、播放切换、预置角色初始化、隐藏／恢复与明确退出；让无语音也可用。
4. **完成资源准备。** 在首个大资源下载前落实目录选择、Windows 总目录启动入口与安装器保留规则；用 ipull 先接一条较简单的 ASR 模型下载，建立组件版本、兼容检查及准备后启用流程，再接 GPT-SoVITS 预制环境、依赖更新和模型，完善功能引导及进度界面。
5. **完成旧版导入。** 覆盖基础模型、角色和聊天，复用资源处理流程，再验证缺文件、取消和重复导入。
6. **检查完整使用流程并美化。** Electron 和 WebUI 使用同一套业务组件；接入主程序的平台更新工具，重点检查首次启动、下载续传与失败重试、组件更新中断与旧版本保留、切换聊天、隐藏恢复，以及 Windows 更新与卸载后资源仍在、macOS ad-hoc 版本更新后可以重新启动。
